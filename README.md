# VendorFlow

VendorFlow is a form-first, deterministic vendor-onboarding demonstration for the Zamp ASA PS-2 case study. It returns **Approved**, **Pending**, or **Rejected** with visible rule outcomes and a follow-up draft. It uses fictional `VF-DEMO` inputs only.

It is not a GSTN, PAN, IFSC, bank, legal, identity, or sanctions verification product. The PDF upload is optional; a form-only happy path is approved without one. Gemini is deliberately not implemented in P0 and `GEMINI_ENABLED=false` remains the default.

## Run locally

Use Python 3.14 where available (3.12–3.14 is supported by the app logic):

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt
Copy-Item .env.example .env
streamlit run app.py
```

## Tests and linting

```powershell
$env:PYTHONPATH = "src"
pytest -q
ruff check src tests app.py
```

## Spot-check vendors

`New run` includes ten fictional vendors, each with its own legal name, GSTIN, PAN and account number, so no two collide. Pick one in **Spot-check vendor**, load it, and run it:

| Vendor | Expected | Why |
|---|---|---|
| VF-DEMO Meridian Freight | Approved | clean form, no document |
| VF-DEMO Saffron Logistics | Approved | clean form, different state code |
| VF-DEMO Kiran Traders | Pending | `NAME_VS_BANK_ACCOUNT` |
| VF-DEMO Veer Tools | Pending | `GSTIN_FORMAT` |
| VF-DEMO Nova Ceramics | Pending | `GSTIN_STATE_MISMATCH` |
| VF-DEMO Northwind Papers | Pending | `PAN_FORMAT` |
| VF-DEMO Orbit Components | Pending | `IFSC_FORMAT` |
| VF-DEMO Bluewave Chemicals | Pending | `BANK_ACCOUNT_FORMAT` |
| VF-DEMO Stonebridge Metals | Pending | `EMAIL_FORMAT` |
| VF-DEMO Pinnacle Holdings | Rejected | demonstration blocklist |

Each vendor can be run once. Running the same vendor a second time is a genuine duplicate and will correctly return Pending `DUPLICATE_VENDOR` — that is the rule working, not a bug.

Every spot-check vendor also has two bundled optional PDFs: a matching one (same legal name and GSTIN, so the decision is unchanged) and a conflicting one (same legal name, different GSTIN prefix, so the run becomes Pending `DOCUMENT_VS_FIELDS`). Load a vendor, then pick either document in **Or use a bundled fictional PDF**. The lists are generated by `python scripts/make_demo_pdfs.py` and committed to `tests/fixtures/pdfs/`.

## Optional PDF fixtures

The form remains the primary workflow. To generate the two small, fictional PDFs used for the document-consistency demo, run:

```powershell
python scripts/make_demo_pdfs.py
```

In **New run**, select either bundled PDF. The matching document remains Approved; the intentionally conflicting GSTIN document becomes Pending with `DOCUMENT_VS_FIELDS`.

## Supabase (optional persistence)

This repository never applies remote database changes. In the existing **vendorflow-dev2** Supabase project, open the SQL Editor and run [`supabase/migrations/20261020_001_vendorflow_p0.sql`](supabase/migrations/20261020_001_vendorflow_p0.sql).

Then set these Streamlit Community Cloud secrets (or the equivalent values in local `.env`):

```toml
SUPABASE_URL = "https://YOUR-PROJECT.supabase.co"
SUPABASE_ANON_KEY = "YOUR-ANON-KEY"
GEMINI_ENABLED = "false"
```

The migration grants anon read/insert policies only for synthetic demo data. This is intentionally not production-secure. Do not use a service-role key. If configuration or persistence fails, VendorFlow shows an honest banner and stores the run only in browser session state.

## Deploy

Push this repository to GitHub, create a Streamlit Community Cloud app with `app.py` as the entrypoint, add the secrets above in Advanced settings, and verify the hosted URL. The app works without Supabase as a form/demo fallback.
